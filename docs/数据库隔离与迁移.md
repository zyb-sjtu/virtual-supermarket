# 数据库隔离与迁移说明（v1.4）

## 当前状态

系统已从内嵌 SQLite 切换为独立 PostgreSQL 服务。网页后端通过 TCP 连接数据库，网页端不持有数据库连接或凭据。

| 隔离层次 | 当前结果 |
| --- | --- |
| 浏览器与数据库访问隔离 | 浏览器调用 HTTP API，由后端执行数据库事务 |
| 后端与数据库服务分离 | 已完成：HTTP 8000，PostgreSQL 5433，不同进程 |
| 两套数据库实例隔离 | 已验证：5433 主库、5434 验证库，独立进程和数据目录 |
| 数据库搬迁 | 已验证 pg_dump/pg_restore 备份恢复、全表字段核对与后端连接切换 |
| 跨物理主机部署 | 连接配置已支持；本轮只进行同机不同端口模拟，尚未实测云部署 |
| 商家/客户权限、不同商店隔离 | 尚未实现，当前为单店共用操作能力 |

## Agent 确认表（P2）

`agent_confirmations` 保存 Agent 高风险写操作的确认令牌、参数指纹、预览和过期/消费时间。它属于可丢弃的临时状态，不是业务账本：

- SQLite 在 `db._migrate_business` 中增量创建（schema 版本 4）；PostgreSQL 在 `postgres_schema.py` 中创建，版本同样记为 4。
- 该表不参与 SQLite→PostgreSQL 业务数据迁移；测试清空 `shop_test` 时包含该表。
- 正式库首次运行新代码前仍按上文流程备份；回退时停服务后执行 `DROP TABLE agent_confirmations` 即可，商品、订单、库存、台账和审计表不受影响。
- 过期令牌按 24 小时清理；`ConfirmationStore.reset()` 仅用于测试，并拒绝非 `shop_test` 的 PostgreSQL。

## 如何从本地搬出去

1. 在目标主机安装 PostgreSQL，创建数据库和业务账号，配置网络与连接权限。
2. 本地使用 `postgres_maintenance.py backup` 生成归档，不直接复制运行中的数据库目录。
3. 将归档传到目标主机，在空业务数据库用 `postgres_maintenance.py restore` 恢复。
4. 运行一致性检查并核对商品、库存、订单、图片、台账和请求去重数据。
5. 设置后端 `PGHOST`、`PGPORT`、`PGDATABASE`、`PGUSER` 及凭据即可连接目标主机。HTTP 地址与端口仍由 `SHOP_HOST`、`SHOP_PORT` 单独配置。
6. 最终切换先停旧入口写入、生成最终备份并恢复，再启新入口；保留旧库与备份用于回退。

当前业务 API 与前端无需再次改造。真实跨主机部署还需要证书、访问规则、账号权限和运维配置；用户身份权限仍属于后续开发。

## 本轮验证证据

- 原 SQLite 数据完整迁入 5433：3 个商品、45 件库存、3 个订单、7 条交易/补货记录、10 条台账，净销售额 ¥29.50。
- 5433 一致备份恢复到 5434，全部业务表逐字段摘要一致。
- 在 5434 新增商品并交易，5433 的全部业务表摘要不变。
- 停止 5434 时，8001 网页仍可打开，数据/写入返回 503；8000/5433 不受影响。
- 重启 5434 后数据完整保留，网页后端自动重连，没有将失败操作保存到 SQLite。
- 28 项 SQLite 回归与 15 项 PostgreSQL 测试、PostgreSQL 网页交互验证通过。

保留的 `data/shop.sqlite3` 是迁移来源，不再用于正式写入。迁移前备份为 `data/backups/pre-business-20261014.sqlite3`，PostgreSQL 搬迁验证归档为 `data/backups/shop-pg-20261014.dump`。

完整安装、启动、备份迁移和验证命令见 [PostgreSQL运行与隔离验证](PostgreSQL运行与隔离验证.md)，机器可读证据见 [postgresql-validation.json](postgresql-validation.json)。
